# Полный расчёт на независимых колонках

`column_heat_forward` решает уравнение теплопереноса на C-сетке, затем обновляет
интегралы EASY%Ro. Старый `heat_forward` сохранён отдельно. Для новой ветви
используются BDF1, Пикар, компактная линейная схема или conservative NMPFA.

Пример:

```bash
python3 tools/prepare_forward_data.py local/forward_problem_data/data1 local/results/data1/cgrid_input
./build/release/column_heat_forward local/results/data1/cgrid_input local/results/data1/cgrid_run \
  --dx 100 --dz 100 --dt-ma 0.5 --rdp-tol 5 --scheme linear --linear-solver umfpack
uv run python tools/view_column_snapshots.py local/results/data1/cgrid_run --field temperature
```

`--rdp-tol 0` (по умолчанию) сохраняет исходные границы; положительное значение
в метрах упрощает общие контакты с сохранением выклиниваний. `--pinchout positive`
оставляет ячейкам минимальную высоту `--min-height` за счёт других ячеек той же
колонки. `--pinchout zero` исключает схлопнувшиеся ячейки из СЛАУ в момент их
нулевой толщины. Доступны `--linear-solver umfpack|gamg|boomeramg`.
Допуск Пикара задаётся `--picard-rtol` (по умолчанию `1e-8`).
Для отдельной проверки влияния сетки `--axis-rdp-tol` сокращает узлы колонок
по RDP, но оставляет исходные функции границ: их средняя глубина в каждой
колонке вычисляется по всем исходным узлам. Без этой опции ось следует за
геометрией, выбранной `--rdp-tol`. В обоих режимах точки скачков литотипа
остаются обязательными границами колонок.

Внутри эпохи номера ячеек постоянны. До рождения нового слоя его объём относят
к локально верхнему старому слою. На границе эпох температуру интерполируют по
пространству; интегралы зрелости старых слоёв переносят только из того же слоя,
а у нового слоя обнуляют. Это принятое правило реконструкции между снимками.

`summary.txt` появляется после успешного завершения расчёта. `snapshot_*.cgrid`
содержат начальное состояние и состояния до и после каждого перехода эпох.
Формат версии 1 — little-endian, массивы в порядке ячеек: magic `CGRID001`,
`uint32 kind` (0/1/2), `float64 age_ma`, `uint64 nx`, `uint64 ncells`,
`uint32 nreactions`; затем `float64 x[nx]`, `uint64 column[ncells]`,
`int32 layer_id[ncells]`, `float64 z_top[ncells]`, `z_bottom[ncells]`,
`temperature[ncells]`, `reflectance_percent[ncells]`,
`maturity_integrals[ncells*nreactions]`. Интервалы по x берутся из `x[column]`
и `x[column+1]`.

`maximum_cell_residual` показывает наибольшую абсолютную невязку ячейки в ваттах
на единицу поперечной длины. `maximum_global_balance` сравнивает накопление с
внешними потоками и источником; `maximum_internal_flux_defect` проверяет
совпадение двух сторон внутренних вертикальных граней. `summary.txt` также
сохраняет настройки сетки, схемы и решателя для повторения расчёта.

## Проверка и выбор настроек

Сравнимые расчёты ниже используют шаг времени `2 Ma`, положительную минимальную
высоту ячейки `0,01 м` и UMFPACK; шаги по x и z указаны отдельно.
Для повторения полного расчёта на исходной геометрии с разреженной осью:

```bash
./build/release/column_heat_forward <input-dir> <output-dir> \
  --dx 50 --dz 75 --dt-ma 2 --rdp-tol 0 --axis-rdp-tol 5 \
  --pinchout positive --min-height 0.01 --scheme linear --linear-solver umfpack
```

Расчёты `data1` и `data2` на исходных границах и с RDP(5) завершались при BDF1,
линейной схеме и UMFPACK. На тестовых C-сетках проверен первый порядок BDF1,
в том числе при движущейся ячейке. Вариант
с точно нулевой толщиной прошёл оба набора данных; на
грубой сетке его отличие от малой положительной толщины в финальной температуре
составило менее 0,05 K RMS. Изменение минимальной высоты от `0,001` до `0,1` м
меняло финальную температуру не более чем на `0,15 K` RMS относительно варианта
с точно нулевой высотой. Глобальный баланс в этих расчётах был лучше `1e-8`.

После сохранения в оси точек смены литотипа на RDP(5) разность линейной схемы
и NMPFA при сгущении `(100,150)` → `(50,75)` м убывает на `data1` с `1,638`
до `0,473 K` RMS (`1,79` по `log₂` отношения), на `data2` с `2,598` до
`0,676 K` RMS (`1,94`). На мелкой сетке это `0,40%` и `0,61%` размаха
температуры. Это сходимость разницы схем, а не оценка ошибки каждой схемы.
На `data2` NMPFA также посчитан с исходной геометрией при той же разреженной оси,
что и линейная схема: разность финальной температуры `0,628 K` RMS (`0,56%`
размаха), `%Ro` — `0,0164` процентного пункта RMS; глобальный баланс
`2,0e-12`. Контрольная схема заняла `73,9` с против `13,5` с линейной
схемы в этих запусках.
При дополнительном сгущении линейной схемы `(50,75)` → `(25,37.5)` м
финальная температура меняется на `0,663 K` RMS на `data1` и `0,657 K` RMS
на `data2`, примерно `0,6%` размаха. Поле `%Ro` меняется на `0,0050` и
`0,0047` процентного пункта RMS. Это сеточная устойчивость в исследованном
диапазоне, без известного точного решения полной задачи.

Для проверки RDP исходную и упрощённую геометрию считали на **одинаковой**
оси колонок. При `(50,75)` м разность температуры составляет `0,102 K` RMS
на `data1` и `0,138 K` RMS на `data2` (`0,09%` и `0,12%` размаха). Локальные
максимумы достигают `5,68` и `7,09 K`, поэтому для конкретных точек наблюдения
упрощение ещё следует проверить. Прежнее сравнение `data2` давало `6,94 K`
RMS (`5,3%`), но в нём исходная геометрия создавала намного более плотную ось;
это число нельзя считать чистой ошибкой RDP. Ось можно разрежать отдельно через
`--axis-rdp-tol`, сохраняя исходные функции границ и точки смены литотипа.
В парном замере `data2` на одинаковой оси RDP(5) занял `12,8` с против
`13,5` с исходной геометрии, выигрыш около `5%`. Поэтому RDP остаётся опцией,
а рабочий проверочный режим сейчас использует исходную геометрию с
`--axis-rdp-tol 5`.

UMFPACK служит надёжным вариантом для проверки. На RDP-сетках `(100,150)` м
GAMG прошёл оба набора данных и практически совпал с прямым решателем. На
исходной геометрии `data2` с осью по всем её узлам GAMG достиг лимита итераций
уже на первом шаге. На разреженной оси с сохранёнными точками смены литотипа
полный `data2` расчёт `(50,75)` м с GAMG завершился: финальная температура
отличается от UMFPACK на `1,1e-11 K` RMS. При этом GAMG потребовал `77385`
линейных итераций и `25,4` с против `581` прямого solve и `13,5` с в отдельном
замере UMFPACK; эти времена ориентировочны, поскольку запуски выполнялись не
как строгий benchmark. На более крупных сетках настройки PETSc ещё надо
сравнить по времени и памяти.
Детальные результаты исследований хранятся в `local/results`.
