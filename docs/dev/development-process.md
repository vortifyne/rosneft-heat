# Разработка проекта

## Основной порядок работы

1. Выбрать задачу из [бэклога](backlog.md) и уточнить ожидаемый результат.
2. Изменять только относящиеся к задаче модули и сохранять их архитектурные границы.
3. Отформатировать изменённый код с помощью `clang-format`.
4. Собрать Release и выполнить относящиеся к изменению проверки.
5. Обновить документацию, если изменились команды, форматы, физические соглашения или устройство
   программы.

Для исследования, которое ещё не стало частью программы, используется `local/`. В `docs/`
переносится только принятое и самостоятельно читаемое описание.

## Сборка и проверки

Основной воспроизводимый путь:

```bash
make docker-release
make docker-test
```

Отладочная сборка:

```bash
make docker-debug
```

Измерения быстродействия и полные расчёты выполняются в Release. Google Benchmark применяется
для малых повторяемых измерений отдельных операций. `clang-tidy` запускается перед принятием
значительных изменений или при проверке конкретной проблемы.

## Стиль C++

- функции и переменные — `snake_case`;
- классы и структуры — `PascalCase`;
- константы — `kConstant`;
- приватные поля оканчиваются подчёркиванием;
- форматирование задаётся `.clang-format`;
- лишние копии, выделения памяти и виртуальные вызовы не добавляются в циклы по ячейкам, граням
  и степеням свободы.

## Архитектурные правила

- Общие линейные и нелинейные решатели не зависят от физической задачи.
- Временная схема работает через `SemiDiscreteSystem`.
- Модельная и бассейновая задачи находятся в разных модулях.
- Формулы теплофизических свойств не зависят от сетки и ввода-вывода.
- Управление эпохами, перестроением сетки и сохранением результатов находится в `src/basin/`.
- Для рабочего сценария поддерживается один выбранный способ решения; новый вариант добавляется
  только при явной необходимости.

Подробное разделение кода приведено в
[обзоре архитектуры](../reference/architecture-overview.md).

## Проверка изменений

Объём проверки определяется риском изменения:

- для формулы или численного метода нужен тест с независимым ожидаемым результатом;
- для исправления ошибки нужен пример, воспроизводящий её до исправления;
- для изменения сетки или переноса дополнительно проверяются положительность площадей и
  глобальный баланс энергии;
- для оптимизации сопоставляются результат и время с прежним вариантом;
- для изменения команды запуска выполняется короткий расчёт по опубликованной команде.

Пройденные тесты подтверждают только проверенные случаи. Ограничения принятого решения следует
записывать рядом с его описанием, если они влияют на использование программы.

## Документация

- `docs/user/` содержит только команды и описание результатов;
- `docs/reference/` содержит действующие физические и численные соглашения;
- `docs/dev/` содержит порядок разработки, направления работ и текущие задачи;
- `docs/reference/drafts/` является архивом и не описывает текущее состояние программы.

Одно соглашение описывается в одном основном месте. Остальные документы ссылаются на него.
История обсуждения, промежуточные планы и результаты отдельных запусков в справочную
документацию не входят.
