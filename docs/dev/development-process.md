# Разработка

## Сборка и проверки

Нужны Docker и GNU Make. Из корня репозитория:

```bash
make docker-image
make docker-release
make docker-test MODEL=ON
```

Образ собирается один раз. Программы `basin_forward_solver` и `basin_inverse_solver`
находятся в `build/docker/release/`.
Для отладочной сборки используется `make docker-debug`, число параллельных заданий задаётся
через `JOBS`. Без `MODEL=ON` модельная задача не собирается; тесты включаются целью `docker-test`.
Три группы тестов проверяют общие методы, бассейновую и модельную задачи.
Проверки Python запускаются отдельно: `uv run --frozen python -m unittest discover -s tests/tools`.

Цели `local-release` и `local-test` собирают код без Docker. Для них нужны компилятор C++20,
CMake, Ninja, PETSc и MPI; путь к vcpkg задаётся переменной `VCPKG_ROOT`.

## Правила кода

- Код, комментарии и сообщения программы пишем на английском, документацию — на русском.
- Типы именуются в `PascalCase`, функции — в `snake_case`, константы — в `kConstant`.
- Для физических и математических величин используются краткие согласованные обозначения.
- Приватные поля оканчиваются подчёркиванием; форматирование задаёт `.clang-format`.
- В вычислительных циклах избегаем лишних копий, выделений памяти и повторных проверок
  гарантированных условий.

## Границы модулей

Цели CMake соответствуют модулям:

- `heat_numerics` — линейные и нелинейные решатели, интегрирование по времени; `heat_opt` — POUNDERS.
- `basin_physics` — свойства материалов и EASY%Ro.
- `basin_data` — входные данные, геометрия, сетка, перенос полей и двоичные снимки.
- `basin_heat_forward` — дискретизация, прямой расчёт и его вывод.
- `basin_heat_inverse` — параметры потока, наблюдения и подбор через общий оптимизатор.
- `basin_forward_app` и `basin_inverse_app` — исполняемые программы `basin_*_solver`.

`src/numerics/` не зависит от физической задачи. В `src/model/` находится отдельная модельная
задача для проверки общих методов. Геометрия и описание сеток эпох готовятся один раз;
`set_parameters()` меняет поток, `solve()` начинает новый расчёт с начального состояния.

## Проверка изменений

Изменённый код форматируем с помощью `clang-format`, собираем Release и запускаем относящиеся
к изменению тесты. Формулы и потоки проверяем на известных решениях и по балансу энергии;
сетку — по сохранению площади, перенос — по точности полей и сохранению истории зрелости.
При ускорении сравниваем результат и время на одной машине.

Исследования и результаты отдельных запусков хранятся в `local/`. В документации оставляем
команды использования и устойчивые соглашения. Текущие работы перечислены в [списке задач](backlog.md).
