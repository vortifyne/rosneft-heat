# Процесс разработки

Документ фиксирует базовые правила разработки проекта. Более детальные решения по архитектуре, численным методам, форматам входных данных и пользовательскому интерфейсу описываются в отдельных документах.

## Общие принципы

Проект разрабатывается как консольное приложение на C++ с целевой платформой Linux.

Код должен быть разделён на слабо связанные модули. Каждый модуль отвечает за ограниченную область ответственности и взаимодействует с другими модулями через явно заданные интерфейсы. Внутренние детали реализации не должны протекать в соседние компоненты без необходимости.

На верхнем уровне программа разделяется на вычислительные компоненты:

```text
Решатель обратной задачи
    └── Решатель прямой задачи
          ├── Интегрирование по времени
          ├── Решение нелинейных систем
          │     └── Решение линейных систем
          │           └── Предобуславливатель
          ├── Пространственная дискретизация
          ├── Работа с геометрией и сеткой
          ├── Вычисление теплофизических коэффициентов
          ├── Модель зрелости EASY%Ro
          ├── Диагностика, статистика и профилирование
          └── Ввод и вывод данных
```

Вычисление теплофизических коэффициентов включает процедуры, которые по литотипам, пористости, температуре и параметрам модели определяют коэффициенты уравнения теплопереноса: объёмную теплоёмкость, теплопроводность, источники тепла и связанные физические величины.

Для каждого компонента в первой рабочей версии выбирается один надёжный вариант реализации. При этом интерфейсы должны позволять в дальнейшем сравнивать и заменять алгоритмы внутри компонента без переписывания остальной программы.

## Инструменты

Базовый набор инструментов:

- C++;
- CMake;
- CMake Presets;
- vcpkg;
- CTest;
- clang-format;
- clang-tidy;
- GoogleTest;
- Google Benchmark.

Проектная конфигурация должна позволять запускать форматирование, статический анализ, тесты и бенчмарки воспроизводимым способом.

Сторонние зависимости по возможности подключаются через vcpkg. Общие настройки сборки хранятся в `CMakePresets.json`; локальные настройки разработчика хранятся в `CMakeUserPresets.json` и не коммитятся.

## Стиль кода

Имена переменных и функций пишутся в `snake_case`.

Имена классов и структур пишутся в `PascalCase`.

Имена констант пишутся в форме `kConstant`.

Приватные поля класса помечаются завершающим подчёркиванием: `field_`.

Приватные функции не получают специального префикса или суффикса.

Форматирование кода задаётся `clang-format`.

`clang-tidy` используется для периодического статического анализа и проверки значимых изменений. Его не требуется запускать после каждой мелкой правки, если это делает локальный цикл разработки слишком медленным.

## Документация

Документация хранится в каталоге `docs/`.

Каталог `docs/dev/` содержит материалы по разработке: процесс, дорожную карту, бэклог, заметки по отдельным задачам и техническим решениям.

Каталог `docs/reference/` содержит справочные материалы по математической модели, численным методам, архитектуре вычислительных компонентов и форматам данных.

Каталог `docs/user/` содержит пользовательскую документацию: запуск приложения, формат входных данных, параметры командной строки и описание результатов.

Если тема уже описана в одном документе, другие документы должны ссылаться на него, а не дублировать содержание.

## Бэклог

Актуальные задачи ведутся в `docs/dev/backlog.md`.

Задачи должны иметь стабильный идентификатор. Рекомендуемый формат:

- `CORE-001` для ядра приложения и общих вычислительных компонентов;
- `IO-001` для ввода и вывода данных;
- `MESH-001` для геометрии и сеток;
- `PHYS-001` для теплофизических моделей;
- `TIME-001` для интегрирования по времени;
- `NLS-001` для нелинейных решателей;
- `LIN-001` для линейной алгебры;
- `INV-001` для обратной задачи;
- `PERF-001` для профилирования и анализа производительности;
- `TEST-001` для тестов;
- `BENCH-001` для бенчмарков;
- `DOC-001` для документации.

Другие идентификаторы также можно использовать, придерживаясь такого стиля.

В бэклоге должны быть отдельные таблицы для актуальных и выполненных задач. Для каждой актуальной задачи указываются идентификатор, приоритет, статус, краткая формулировка и критерий выполнения.

Если задача требует подробного описания, рядом с бэклогом создаётся отдельная заметка в `docs/dev/task-notes/`. В бэклоге указывается ссылка на эту заметку.

Заметки по завершённым задачам при необходимости переносятся в `docs/dev/task-notes/done/`. В таблице выполненных задач сохраняется ссылка на итоговую заметку.

## Готовность изменений

Правила готовности зависят от типа изменения. Экспериментальный код, прототип численного метода и изменение устойчивого интерфейса требуют разного уровня проверки.

Всегда:

- изменение должно решать заявленную задачу или явно фиксировать промежуточный результат;
- код должен быть понятен для дальнейшей доработки;
- не должны ломаться уже известные рабочие сценарии без явного решения изменить их поведение.

Обычно:

- код форматируется через `clang-format`;
- для устойчивого поведения добавляются или обновляются тесты;
- локально запускаются релевантные тесты через CTest;
- документация обновляется, если изменились интерфейсы, процесс запуска, формат данных или архитектурные решения.

По необходимости:

- `clang-tidy` запускается для значимых изменений, перед стабилизацией модуля или при подготовке крупного коммита;
- бенчмарки запускаются для изменений, которые могут заметно повлиять на производительность;
- для оптимизаций указывается способ сравнения с базовым вариантом;
- прототипный код перед переводом в устойчивую часть проекта покрывается тестами и приводится к общему стилю.
